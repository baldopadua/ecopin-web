# Session hardening: first slice

VULN-02 remains open. Normal access tokens still use `localStorage`, and the separate Supabase client still has its existing session-persistence configuration. This change only removes persistence of the custom backend's temporary password-change and refresh credentials. It does not establish server-side authorization, token lifetime/rotation/revocation guarantees, or protection against an active same-origin script compromise. [OWASP storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html#local-storage) explains why browser-readable session identifiers remain a risk.

`lib/auth-token.mjs` now keeps those two secondary credentials in document memory. Legacy localStorage/sessionStorage entries are removed rather than restored. SPA navigation preserves the temporary credential for password change; reloading or opening another tab requires signing in again. Refresh credentials are lost on full reload too; the remaining access token can work until it expires, after which fresh sign-in is required. A new login replaces the previous secondary credentials.

Successful password change clears credentials and returns to sign-in, rather than promoting a temporary token to a normal session. Sign-out clears local credentials before waiting for the backend; session-expiry paths use the same central cleanup. Cross-tab access-token changes clear secondary credentials. Pending refresh responses are ignored after those credentials have changed, so stale failures cannot clear a newer login and stale successes cannot restore a signed-out session. Backend logout is still best-effort and its revocation behavior has not been certified.

Run `npm run test:session-credentials` for the synthetic lifecycle/race tests, also included in `npm test`. After a production build and local start, the existing `tests/password-recovery.browser.cjs` and `tests/public-pages.browser.cjs` scripts exercise the actual sign-in UI using mocked login/password/service responses. Set `ECOPIN_TEST_URL=http://127.0.0.1:4017` and provide Playwright through NODE_PATH or ECOPIN_PLAYWRIGHT_PATH. Those scripts block external requests and WebSockets.

The remaining migration needs a server-managed staff session, bounded HttpOnly/Secure/SameSite cookies, CSRF/origin checks, and a server-side API/media boundary that keeps access/refresh credentials away from browser JavaScript. Deployment and separate authority-side expiry/revocation checks remain outstanding.
